# How HwProbe works

Implementation notes for the engines, caches, and suggestions. How to build, test, and release is in `DEVELOPMENT.md`. The performance tests are called speed runs in the code.

## Performance tests (speed runs)

- `SpeedEngine` measures every chosen output (a codec at a player quality, or decode only) from every chosen input on each chosen backend and software, and reports each result as it finishes.
- Arguments come from `EncodingHelper` with `ProbeCell.FullQuality`, as a real request gets them. The output size goes through Jellyfin's `ResolutionNormalizer`, as `StreamingHelpers` does.
- `SpeedCommandLine` loops the inputs and bounds each run with `-t`. `SpeedMeter` counts speed and concurrent streams, and is tested without ffmpeg. A copy keeps up when it holds real time from its first frame on (`FrameTiming.SteadyFps`, from when `-progress` reports arrive), so start-up is neither counted nor excused.
- Resources (off by default; the Resource Usage setting, or `--speed-resources` in the CLI): the single copy whose speed is reported is also measured for CPU time, peak memory, and GPU engine time (`FfmpegInvocation.MeasureResources`, `src/HwProbe.Core/Resources`). Windows puts it in a job object (Meziantou.Framework.Win32.Jobs) for CPU and peak memory across its tree, and reads the GPU Engine performance counters' Running Time per engine type (PDH, every vendor). Linux samples `/proc/[pid]/stat`, `status` (VmHWM), and DRM `fdinfo` engine time (i915 and amdgpu from kernel 5.19, xe from 6.8); NVIDIA has no fdinfo engine stats, so NVML's whole-GPU encoder, decoder, and SM use stands in, marked `GpuWholeDevice` (NVML's per-process figures are empty in containers). macOS samples `proc_pid_rusage` and has no GPU figures: VideoToolbox works on the media engine, whose use macOS doesn't report without root, and per-process GPU time needs a task port only root gets. Sampling runs every 200 ms because Linux and macOS forget a process once it exits. A failed sample, a missing system library, or a job the process can't join leaves the figures out rather than failing the measurement; nothing may escape the sampling timer, since that would end the server's process. Peak memory is the platform's own measure: committed private memory of the job on Windows, peak resident memory (VmHWM) on Linux, and lifetime peak physical footprint on macOS. GPU memory: Windows reads the GPU Process Memory counters' Dedicated Usage; Linux sums DRM fdinfo's `drm-resident-*` regions (amdgpu's older `drm-memory-*` before kernel 6.4); NVIDIA on Linux reports how far NVML's whole-GPU memory in use rose above where it started. Test Results' Resource Usage view shows cores in use (CPU seconds over wall seconds), peak memory, the busiest GPU engine, and peak GPU memory; the Resource Usage setting explains, for the server's platform, which figures are the transcode's own and which cover the whole GPU; engine names are labelled from `gpuEngines` in `catalog.yaml`.
- A hardware backend only measures what it encodes (or, for decode tests, decodes) on the GPU.
- Every full measurement (not one cut off by a timeout or the time limit) is saved under `speed-results` beside the clip cache, keyed by a SHA-256 of the measurement method (`SpeedResultCache.MeasurementVersion`, bumped when how a measurement is taken changes), ffmpeg path and version, backend, device, test, library file size and time, accuracy, repeats, whether resource usage is measured, and the ffmpeg command and environment EncodingHelper generates for it (`SpeedResultCache.Key`). Any setting or server change that alters the command misses; GPU driver updates aren't keyed. With **Earlier results: Reuse** (`ReuseResults`, the default on the page), a matching measurement is shown with the date it was made instead of being measured again. Entries from another measurement method or ffmpeg are deleted at the start of each run; deleting the cache deletes them all.
- **When the server starts transcoding** (`WhenTranscoding`): **Cancel** stops the run when a session starts transcoding (`ProbeService.WatchForTranscodeAsync`), keeping finished measurements and marking the report `CancelledForTranscode`; **Keep measuring** ignores transcodes. Both refuse to start during one. The choices and the default (Pause, for the page and the API alike) come from `whenTranscoding` and `defaultWhenTranscoding` in `catalog.yaml`. With **Pause**, the run starts even while a session transcodes and waits for it to end before making clips, opening devices and measuring (`SpeedPause.HoldWhileBusyAsync`, phase `Deferring`; two idle checks in a row end the wait). A transcode starting mid-measurement cancels that measurement, which kills its ffmpeg trees; once nothing transcodes it runs again from the start. The busy check is the plugin's own (`ProbeService.IsTranscoding`), polled every second.
- Test suites (`suites` in `catalog.yaml`): runs that differ in one setting, started with one button (`HwProbe/Suite`; `HwProbe/Suites` lists them as this server would run them). `SpeedSuites` expands a suite into steps (thread-count steps from Auto up to the server's logical CPU count), picks its backends (the configured one and software, one of them, or software alone), and offers it only when they work (Intel low power also requires QSV and a passing low-power encode). A configured VAAPI is replaced by QSV when QSV works on the same device (`BackendPreference`): Jellyfin's Intel guide prefers QSV on GPUs it supports, and the two measured within 10% of each other on a Gen 9 NAS. `ProbeService.StartSuiteAsync` runs the steps one after another at Standard accuracy under one hold of the gate; each step is saved as its own run, stamped with the suite, the step, and the suite's start time, which Test Results uses to compare the steps. Cancelling stops the remaining steps.
- `SpeedAdvisor` draws the Test Results suggestions (`HwProbe/SpeedSuggestions`): the fastest hardware backend (software is never suggested over a working one; QSV is suggested over VAAPI on the same GPU when they measure within 5%, marked `Preferred`, and VAAPI's setting comparisons include QSV runs), outputs where the configured backend falls behind real time, and settings compared between saved runs of this version and ffmpeg that differ in that setting alone (audio and burn-in must match too), on the same inputs, against the server's current value, and whose ffmpeg commands differ (each result keeps a hash of its command). Turning tone mapping off is never suggested; faster values that cost picture quality are marked. A faster value is suggested when every output gained more than 5%; a better-quality preset or CRF when it still keeps 1.5x real time on real video. Test videos encode faster than real video, so headroom is judged on samples and library files only, and suggestions resting on test videos alone say so. `HwProbe/ApplyMeasured` applies a suggested setting through the same history and Revert as the probe's advice.
- A library file comes from the item's media source in the plugin, or from ffprobe with `--speed-file` in the CLI, and is read from a tenth of the way in.

## Test clips and downloads

Test clips are made with the server's ffmpeg and cached per ffmpeg build. A clip that can't be made comes from a copy bundled in the plugin, or from FFmpeg's FATE sample suite, pinned by SHA-256. The cache is under Jellyfin's cache folder in `hwprobe/fixtures`: a folder per ffmpeg build, `samples` (kept across builds) and `downloads` (named by SHA-256). The Help tab lists it through `HwProbe/Cache/Contents` (`FixtureCacheContents`, which names each file from the catalogs). Before each probe or performance test builds clips, `FixtureCacheContents.Prune` deletes other ffmpeg builds' folders, files this version doesn't use, and leftovers of interrupted writes.

- Bundled (no public sample exists): HEVC RExt 4:4:4 10-bit, 4:2:2 12-bit and 4:4:4 12-bit, AV1 10-bit, and H.264 with frequent key frames.
- Always downloaded: `vc1/SA00050.vc1` (no free VC-1 encoder exists).
- Downloaded only when generation fails: `h264-conformance/BA1_Sony_D.jsv`, `h264-conformance/CVFI1_Sony_D.jsv`, `hevc-conformance/WP_A_Toshiba_3.bit`, `hevc-conformance/WP_A_MAIN10_Toshiba_3.bit`, `hevc-conformance/Main_422_10_A_RExt_Sony_1.bin`, `vp9-test-vectors/vp90-2-09-lf_deltas.webm`, `vp9-test-vectors/vp92-2-20-10bit-yuv420.webm`, `vp8-test-vectors-r1/vp80-00-comprehensive-001.ivf`, `av1-test-vectors/av1-1-b8-02-allintra.ivf`.
- For PGS subtitle burn-in: `sub/pgs_sub.sup` (ffmpeg has no PGS encoder).

Film samples for speed runs are downloaded only when chosen: a pinned piece of each Wikimedia Commons file (its WebM header plus whole clusters, two range requests), checked by SHA-256, used as downloaded, and cached apart from the ffmpeg build. The 1080p ones are VP9 with Opus audio: The Man Behind the Machine, Tears of Steel, and Sintel (CC BY 3.0), and Sol Levante (CC BY 4.0). The Man Behind the Machine's piece is live action without visual effects; Tears of Steel mixes live action and CGI. The 4K ones come from Commons' original files: The Man Behind the Machine (VP9), SINGULARITY (HDR10 AV1 Main 10-bit, CC BY 4.0), and Sol Levante's HDR10 AV1 copy (Professional profile, 4:4:4 12-bit, which GPUs don't decode). The 8K one is a whole 10 s file of a Sherman tank at Tankfest 2021 (VP9 8192×4320, no audio, CC BY-SA 4.0); Jellyfin decodes it at 8K and outputs at most 4K (`EncodingHelper.GetFixedOutputSize`). Tears of Steel and Sintel have no 4K piece: their 4K originals are VP8, and Commons transcodes stop at 1080p. Requests carry a descriptive User-Agent, as Wikimedia asks.
