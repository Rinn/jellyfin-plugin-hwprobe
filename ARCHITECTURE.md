# How HwProbe works

Implementation notes for the engines, caches, and suggestions. Building, testing, and releasing are in `DEVELOPMENT.md`. Performance tests are called speed runs in the code.

## Probes and advice

- `ProbeEngine` opens each device, runs its smoke test, then its matrix (`MatrixCatalog.For`). Software runs `MatrixCatalog.Software` last, also when no device opens: BWDIF deinterlacing (`EncodingHelper.GetSwDeinterlaceFilter` takes the method without checking the filter) and key-frame-only decoding for trickplay. A software test passes on exit 0 with frames (`VerdictEvaluator.EvaluateSoftware`), as there is no hardware to confirm. A run limited to a device or backend skips it.
- `SettingsAdvisor` turns each backend's results into advice for every option the Transcoding and Trickplay pages show for it; the software row (`CapabilityReport.Software`) gets the options shown for None. HEVC and AV1 encoding are advised off in software, as CPU encoding of them is slow. Allow subtitle extraction on the fly is advised on everywhere, so text subtitles reach clients instead of being burned in. Apply accepts the software advice when the server is set to None.

## Performance tests (speed runs)

### Measuring

- `SpeedEngine` measures every chosen output (a codec at a player quality, decode only, or images) from every chosen input on each chosen backend and software, reporting each result as it finishes. A hardware backend only measures what it encodes (or, for decode tests, decodes) on the GPU.
- Arguments come from `EncodingHelper` with `ProbeCell.FullQuality`, as a real request gets them; the output size goes through `ResolutionNormalizer`, as `StreamingHelpers` does.
- `SpeedCommandLine` loops the input and bounds each run with `-t`. `SpeedMeter` counts speed and concurrent streams and is tested without ffmpeg. A copy keeps up when it holds real time from its first frame (`FrameTiming.SteadyFps`, from the `-progress` reports), so start-up is neither counted nor excused.
- Measurements are `testDelay` seconds apart (catalog, 1 s) so the system winds down from the last; a reused result doesn't wait.
- Where the probe found a decode failing, runs decode it in software (`SpeedOptions.ForReport`, keyed as the probe names the decode, including QSV's own and CUVID decoders), as Jellyfin does once the advice to untick it is followed.
- Image outputs (Trickplay) extract images as `MediaEncoder.ExtractVideoImagesOnIntervalAccelerated` does (v12.2): EncodingHelper's input, filter, and MJPEG encoder inside a pinned copy of its wrapper (`ArgumentSource.BuildImages`: the key-frame check, input threads, VideoToolbox low priority, the stream map, setpts, and the quality per encoder), at the Trickplay page's settings and the server's first width, interval, and quality scale. Hardware backends run with Enable hardware decoding on, software with it off. The input is bounded (`-t` before `-i`) and the images discarded. Speed is the content over the time taken (`MeterPace.Images`), as the output has few frames; no streams are counted and there's no real time to keep. `ImageArgumentsTests` pins the strings, and `container-plugin.sh` compares the command with the one Jellyfin logs for its own trickplay.
- Double-rate deinterlacing makes a frame per field, so it's measured against twice the source rate (interlaced sources of 30 fps or less, as `EncodingHelper.GetSwDeinterlaceFilter` doubles them), and comparisons use speed against real time rather than frame counts.
- A library file comes from the item's media source in the plugin, or from ffprobe with `--speed-file` in the CLI, and is read from a tenth of the way in.

### Resources and power

- Resource usage (on by default, `defaultMeasureResources`; the Resource Usage setting, or `--speed-resources false`) is sampled every 200 ms on the single copy whose speed is reported (`FfmpegInvocation.MeasureResources`, `src/HwProbe.Core/Resources`); Linux and macOS forget a process once it exits. A failed sample, missing library, or job that can't be joined leaves the figures out instead of failing the measurement, and nothing may escape the sampling timer, as that would end the server's process.
  - Windows: a job object (Meziantou.Framework.Win32.Jobs) for CPU and committed private memory across the tree; GPU Engine Running Time per engine type and GPU Process Memory Dedicated Usage from PDH, every vendor.
  - Linux: `/proc/[pid]/stat`, VmHWM, and DRM `fdinfo` engine time (i915 and amdgpu from kernel 5.19, xe from 6.8) and `drm-resident-*` memory (amdgpu's `drm-memory-*` before 6.4). NVIDIA has no fdinfo engine stats, so NVML's whole-GPU encoder, decoder, and SM use stand in, marked `GpuWholeDevice` (NVML's per-process figures are empty in containers), and GPU memory is how far whole-GPU use rose.
  - macOS: `proc_pid_rusage` with lifetime peak physical footprint; no GPU figures, as media-engine use and per-process GPU time need root.
- The Resource Usage view shows CPU as a percentage with 100% per core (CPU seconds over wall seconds, as top and Activity Monitor count it), peak memory, the busiest GPU engine (named from `gpuEngines`), and peak GPU memory; a resource no result has gets no column. The setting's help says, per platform, which figures are the transcode's own and which cover the whole GPU.
- Power (`EnergyMeter`) reads whole-device energy meters that need no root, before and after the measured copy, after a 1-second idle reading that serves 30 seconds of measurements: NVIDIA total energy through NVML (Volta and newer), the CPU package through Windows' Energy Meter counters (RAPL, picowatt-hours) or Linux powercap `package` zones (usually root-only or masked in containers), Intel discrete GPUs through hwmon `energy1_input` (kernel 6.2+), and AMD GPUs through hwmon `power1_input` or `power1_average`, which report watts only, so `EnergySpan` samples them every 200 ms and sums the energy (untested; on APUs it includes the CPU). Results keep joules and idle watts by domain (`Cpu`, `Gpu`); the page shows watts above idle and `ResourceComparison` compares energy per frame above idle. Power only counts as a saving, never a cost, since the idle reading can run high after a busy run.

### Saved measurements

- A full measurement (not cut off by a timeout or the time limit) is saved under `speed-results` beside the clip cache and reused by single runs and suites alike when Earlier results is Reuse (`ReuseResults`, the page's default), shown with the date it was made.
- The key (`SpeedResultCache.Key`) is a SHA-256 of `SpeedResultCache.MeasurementVersion` (bumped when how a measurement is taken changes), ffmpeg path and version, backend, device, test, library file size and time, accuracy, repeats, whether resources are measured, and the command and environment `EncodingHelper` generates. Any change that alters the command misses; GPU driver updates aren't keyed.
- Runs and measurements are saved as compact JSON, nulls left out (`SpeedJsonContext.Files`); indented files from earlier versions still load.
- Entries from another measurement version or ffmpeg are deleted at the start of each run. The history keeps the latest 250 runs.
- Help deletes them on their own (`HwProbe/SpeedResults`), keeping runs and clips; Delete clips keeps them, since the key doesn't depend on the clip file.

### When the server transcodes

- `WhenTranscoding`, with choices and default (Pause) from `whenTranscoding` and `defaultWhenTranscoding`. The busy check is the plugin's own (`ProbeService.IsTranscoding`), polled every second.
  - Pause: the run starts even during a transcode and waits for it to end before making clips, opening devices, and measuring (`SpeedPause.HoldWhileBusyAsync`, phase `Deferring`; two idle checks in a row end the wait). A transcode starting mid-measurement cancels it, killing its ffmpeg trees, and it runs again once nothing transcodes.
  - Cancel: stops the run (`ProbeService.WatchForTranscodeAsync`), keeping finished measurements and marking the report `CancelledForTranscode`.
  - Keep measuring: ignores transcodes. Cancel and Keep measuring refuse to start during one.

### Test suites

- `suites` in the catalog: runs that differ in one setting, started with one button (`HwProbe/Suite`; `HwProbe/Suites` lists them as this server would run them).
- `SpeedSuites` expands a suite into steps (thread-count steps from Auto up to the logical CPU count; each step's options over the suite's shared `options`; every suite but VBR audio copies the audio), picks its backends (the configured one and software, one of them, or software alone), and offers it only when they work (Intel low power also requires QSV and a passing low-power encode).
- A configured VAAPI is replaced by QSV when QSV works on the same device (`BackendPreference`): Jellyfin's Intel guide prefers QSV, and on a Gen 9 NAS QSV matched VAAPI at decoding, was 7–15% faster at H.264, and about 2.8 times as fast at HEVC.
- `ProbeService.StartSuiteAsync` runs the steps in turn at Standard accuracy under one hold of the gate. Each step is saved as its own run, stamped with the suite, step, and suite start time, which Test Results uses to compare them. Cancelling stops the remaining steps.
- When a suite varies one setting and no step has the server's value, that value is added as a last step. A step can name the hardware backends it's for (VPP tone mapping on Intel, VideoToolbox's on Apple); elsewhere it's left out, and software doesn't run it again.
- Progress counts every step's measurements (`SuiteDone`, `SuiteTotal`) and the time since the start (`ElapsedSeconds`).
- The CLI runs suites with `--suite`, on the hardware backend from `--speed-backends` or the first working one in Jellyfin's order; Jellyfin's defaults (and any `--speed-option`) stand for the server's settings, and it prints the resulting suggestions.

### Suggestions

`SpeedAdvisor` draws the Test Results suggestions (`HwProbe/SpeedSuggestions`). Each carries the values it was compared with (`Compared`), so the page shows every suggestion as a table with a row per value. Setting values carry their slowest speed and fewest streams per output (`Speeds`); where a table's rows were measured on more than one output, the page shows a column per output, so a value that wins on one codec and loses on another shows both.

- Backends: the fastest hardware backend; software is never suggested over a working one. Within 5% (`Noise`), QSV is suggested over VAAPI on the same GPU (`Preferred`), and a backend that uses at least 10% less CPU, memory, or (same GPU) GPU engine time or memory, and no more of any, is suggested as more efficient (`ResourceComparison`). Outputs where the configured backend falls behind real time are reported. Outputs that two or more backends measured and none kept real time on are reported apart instead, with the fastest backend (`TooSlowEverywhere`); one backend alone, as in a suite, doesn't show the others would fall behind.
- Settings are compared between saved runs of this version and ffmpeg that differ in that setting alone (audio and burn-in must match), on the same inputs and against the server's value, where the ffmpeg commands differ (each result keeps a hash of its command). VAAPI's comparisons include QSV runs. A setting for one output codec (`outputCodec`: Intel low power and CRF) only counts as a difference on that codec's outputs, so the Intel low power suite, which switches both codecs at once, compares each.
  - A value is suggested as faster when every output gained more than 5%, as more efficient (`EfficientSetting`) when alike but using less, and as better quality while it keeps 1.5× real time on real video and most concurrent streams (the catalog's `advice`; where a count is capped or wasn't counted, speed stands in). Of several better-quality values, only the best that qualifies. Faster values that cost quality are marked; turning tone mapping off is never suggested. A better-quality value (`qualityOrder`, `lowerIsBetter`) that measured more than 5% faster than the other on any output contradicts that order, so it's never suggested.
  - Each setting outside a group ends in one suggestion listing every value compared with the server's (`OneTablePerSetting`), recommending, in order: the option's `recommended` value whenever it was measured (`RecommendedValue`, Auto for the encoding preset, whatever the measurements), the best-quality value that qualifies, a change that measured faster or more efficient, then the server's own value. Each listed value says whether it's the server's and whether its picture is better or worse than the recommended one. On VAAPI, which leaves Auto to the driver, Auto isn't ordered against the other presets. A change that measured only as fast as the server's value, which measured faster than it, isn't recommended. The percentage a recommendation gives is the smallest gain any output measured, which with one run per value is the ratio of the speeds the table shows.
  - Test videos encode faster than real video, so headroom is judged on samples and library files only, and suggestions resting on test videos alone say so.
  - The server's value is reported as current when it wins; a setting where nothing is worth changing ends in `NoChange`, so a suite always has an outcome.
- Bitrate limit: when higher H.264 qualities fall behind on the configured backend, the highest that keeps up is suggested as the Internet streaming bitrate limit (`ServerConfiguration.RemoteClientBitrateLimit`, written as `Streaming:RemoteClientBitrateLimit`), paired with no limit.
- Drawbacks: a better-quality value with a `caveat` comes with a `Compatible` suggestion for the option's `compatibleValue` (VBR audio off). The two, each compared with the other, show as one table.
- Groups: settings that together pick one thing (`settingGroups`: deinterlacing, each method at single and double rate; tone mapping, VPP, VideoToolbox, General, and Off) carry the row each side's runs fall in (`Group`, `Row`) and show as one table. The server's row is found from all the group's settings. Apply on a row (`HwProbe/ApplyMeasuredRow`) sets everything the choice needs in one change, turning off a method that would still take precedence (`SpeedAdvisor.GroupRowChanges`). Tone mapping off can be applied, with the row's `caveat` shown, but is never suggested. A row that falls behind real time can't be applied.
- `HwProbe/ApplyMeasured` applies any value a setting's table lists, except the server's own and one that falls behind real time on an output (a bitrate limit only as suggested), through the same history and Revert as the probe's advice. A setting's rows follow its dropdown's order in jellyfin-web, numbers ascending. Hovering a setting in a suggestion shows jellyfin-web's own description (`description` in the catalog). The recommended row is tinted: the suggested value; in a pair, the better-quality side, else the one that isn't the drawback-free alternative; in a group, the better-quality choice no other better-quality suggestion was preferred over, else the faster one likewise.

## Test clips and downloads

- Test clips are made with the server's ffmpeg and cached per ffmpeg build under Jellyfin's cache folder in `hwprobe/fixtures`: a folder per build, `samples` (kept across builds), and `downloads` (named by SHA-256). A clip that can't be made comes from a copy bundled in the plugin, or from FFmpeg's FATE suite, pinned by SHA-256.
  - Bundled (no public sample exists): HEVC RExt 4:4:4 10-bit, 4:2:2 12-bit and 4:4:4 12-bit, AV1 10-bit, and H.264 with frequent key frames.
  - Always downloaded: `vc1/SA00050.vc1` (no free VC-1 encoder exists), and `sub/pgs_sub.sup` for PGS burn-in (ffmpeg has no PGS encoder).
  - Downloaded only when generation fails: `h264-conformance/BA1_Sony_D.jsv`, `h264-conformance/CVFI1_Sony_D.jsv`, `hevc-conformance/WP_A_Toshiba_3.bit`, `hevc-conformance/WP_A_MAIN10_Toshiba_3.bit`, `hevc-conformance/Main_422_10_A_RExt_Sony_1.bin`, `vp9-test-vectors/vp90-2-09-lf_deltas.webm`, `vp9-test-vectors/vp92-2-20-10bit-yuv420.webm`, `vp8-test-vectors-r1/vp80-00-comprehensive-001.ivf`, `av1-test-vectors/av1-1-b8-02-allintra.ivf`.
- The HDR10 test clips are tagged on the frames with `setparams`: jellyfin-ffmpeg 8.1 drops `-color_primaries` and `-color_trc` given as output options, which left the clips SDR and broke VideoToolbox tone mapping.
- Progress counts only clips that aren't cached (`FixtureBuilder.PendingAsync`). Before clips are built, `FixtureCacheContents.Prune` deletes other builds' folders, files this version doesn't use, and leftovers of interrupted writes.
- The Help tab lists the saved runs (Test Results) and measurements under History, one row each with count and size (`HwProbe/SavedData`), then the cache (`HwProbe/Cache/Contents`, `FixtureCacheContents`, naming each file from the catalogs), and deletes a file with its hash file (`HwProbe/Cache/File`, taking only a folder and name the listing gives). Each of the two rows has its own delete, and Delete clips deletes the cache. `HwProbe/Data` deletes everything HwProbe saved: the report, diagnostics, speed runs, saved measurements, report cache, clips, and the settings history. Both refuse while a probe or performance test runs.
- On shutdown `ProbeService.Dispose` cancels a running probe or performance test without waiting, so its ffmpeg tree is killed instead of outliving the server; the run releases the gate itself.

### Film samples

- Downloaded only when chosen, checked by SHA-256, used as downloaded, and cached apart from the ffmpeg build. Most are a pinned piece of a Wikimedia Commons file (its WebM header plus whole clusters, two range requests). A file used whole records its `size` in the catalog for the page; a piece's size comes from its range. Requests carry a descriptive User-Agent, as Wikimedia asks, and archive.org's redirects are followed.
- 1080p, VP9 with Opus: The Man Behind the Machine (live action without effects), Tears of Steel (live action and CGI), Sintel (all CC BY 3.0), and Sol Levante (CC BY 4.0).
- 4K, from Commons' originals: The Man Behind the Machine (VP9), SINGULARITY (HDR10 AV1 Main 10-bit, CC BY 4.0), and Sol Levante's HDR10 AV1 copy (Professional profile, 4:4:4 12-bit, which GPUs don't decode). Tears of Steel and Sintel have none: their 4K originals are VP8, and Commons transcodes stop at 1080p. The 4K suite decodes all three and encodes them at 40 Mbps, the lowest player quality that keeps 4K output in every codec.
- 8K: a whole 10 s file of a Sherman tank at Tankfest 2021 (VP9 8192×4320, no audio, CC BY-SA 4.0); Jellyfin decodes it at 8K and outputs at most 4K (`EncodingHelper.GetFixedOutputSize`).
- Legacy (marked `legacy`, listed after the library video), real old-format files: from Commons, an MPEG-2 576i camcorder clip (CC0, used whole, the Deinterlacing suite's input) and a 320x240 Theora clip (CC BY-SA 3.0, header plus a range of Ogg pages); from the Internet Archive, uploaded by their creators, an Xvid AVI with packed B-frames (public domain, header to the `movi` list plus a range), a Sorenson Spark FLV, a RealVideo 3 file, and a WMV 9 file (each used whole).
